# 실행 환경: T3 Code

SKILL.md의 동작([SKILL.md](../SKILL.md) "실행 환경")을 T3 Code에서 하는 방법이다. 작업자는 T3 도구(`delegate_task`, `t3_pending_request`, `t3_thread_send` 등)로 띄우고 다룬다. 도구의 정확한 인자는 도구 설명을 따른다.

## 다른 점: 이슈 담당

T3에서는 작업자를 "부모와 같은 체크아웃"(`isolation: "shared"`)이나 "새 worktree"(`isolation: "worktree"`)에만 띄울 수 있다. 관리자의 체크아웃은 메인 저장소라서, 관리자가 구현자의 worktree에 검토자를 직접 붙일 수 없다. 그래서 이슈마다 **이슈 담당**을 하나 둔다.

```
관리자 (메인 저장소)
 └ 이슈 담당   delegate_task(isolation: "worktree")  → 이슈 worktree를 얻는다
     ├ 구현자  delegate_task(isolation: "shared")    → 같은 worktree
     ├ 검토자  delegate_task(isolation: "shared")    → 같은 worktree, 다른 계열
     └ 지적 수정·rebase 작업자도 같은 방법
```

- **관리자**는 SKILL.md 1단계(프런티어), 2단계의 명세 쓰기와 점검, 6단계(PR·병합), 7단계(보고)를 한다. 2단계 3의 "띄우기"는 이슈 담당을 띄우는 것이다.
- **이슈 담당**은 자기 worktree에서 2단계 3(구현자 띄우기)부터 5단계(판정과 수정)까지 하고, 통과하면 결과를 돌려준다. 관리자의 규칙(SKILL.md, 등급, 검토, 수정)을 그대로 따른다. 맡기는 글은 아래 "이슈 담당에게 맡기는 글"이다.
- 이슈 담당의 모델은 관리자와 같게 두고, 강도는 `high` 이상으로 준다. target을 비우면 관리자의 **지금 강도**까지 물려받아 `medium`처럼 낮게 뜰 수 있다. 5단계 판정을 하므로 낮은 모델·강도로 내리지 않는다. 대부분 기다리는 시간이라 사용량은 작지만 Claude 한도에 들어간다([limits.md](../limits.md)).

## 준비

- 이번 스레드에서 처음이면 `orchestrator_capabilities`를 한 번 불러 공급자·모델·옵션 이름을 확인한다. 공급자가 꺼져 있으면(`constraints`) 그 에이전트는 등급 목록에서 건너뛴다.
- 이슈 담당의 worktree는 관리자 체크아웃의 **지금 커밋**에서 만들어진다. 맡기기 전에 메인 저장소의 `main`이 원격과 같은지 확인한다(`git pull`).

## worktree 만들기

따로 하지 않는다. 이슈 담당을 `isolation: "worktree"`로 띄우면 T3가 만든다(경로는 `~/.t3/worktrees/<저장소>/t3-…`, 브랜치 이름은 T3가 붙인다). 이슈 담당이 시작하자마자 `git branch -m <작업 이름>-<slug>`로 브랜치 이름을 바꾸고, `t3_worktree_status`의 경로와 함께 `state.md`에 적는다.

- T3 화면의 스레드 브랜치 표시는 처음 이름 그대로 남는다(T3 도구로는 스레드의 브랜치를 바꿀 수 없다). git의 브랜치 이름이 기준이고, push·PR은 바꾼 이름으로 한다. PR은 T3가 스레드에 알아서 연결한다.

## 띄우기

```
delegate_task(task, title, role, isolation, mode, target)
```

- **이슈 담당**(관리자가 띄움): `isolation: "worktree"`, `mode: "async"`, `role: "implementation"`, `title: "<작업 이름> 담당"`, `target`은 관리자와 같은 공급자·모델에 강도만 `high` 이상(예: `{providerInstanceId: "claudeAgent", model: "<관리자 모델>", options: {effort: "high"}}`). 관리자 모델은 `orchestrator_capabilities`의 `inheritedModel`이다.
- **구현자·검토자·지적 수정·rebase·2차 의견**(이슈 담당이 띄움): `isolation: "shared"`, `role`은 `implementation`·`review`. `title`은 `<작업 이름> 구현`, `<작업 이름> 검토 2`처럼 단다.
- 명세는 파일 경로로 준다: "`<명세 절대 경로>`를 읽고 그대로 하세요."
- 결과의 `taskId`와 `childThreadId`를 `state.md`에 역할과 함께 적는다. 보내기와 정리에 쓴다.

에이전트별 `target`:

| 에이전트 | `providerInstanceId` | `model` | 강도 옵션 |
| --- | --- | --- | --- |
| Claude | `claudeAgent` | 표기의 모델(예: `claude-sonnet-5-5`) | `effort` |
| Codex | `codex` | 표기의 모델 | `reasoningEffort`, fast는 `serviceTier` |
| OpenCode | `opencode` | `provider/model`(예: `opencode-go/deepseek-v4.1-flash`) | `variant` |

- 모델을 정하지 않았으면 `model`을 빼고, 강도를 정하지 않았으면 그 옵션을 뺀다. 옵션 값은 `orchestrator_capabilities`가 보여 준 것만 쓴다.
- **Codex fast**: 켜면 `serviceTier: "priority"`, 끄면 `serviceTier: "default"`([codex-fast.md](../codex-fast.md)). 끌 때도 주는 것은 전역 설정이 fast일 수 있기 때문이다.
- **OpenCode**는 `model`과 `variant`를 직접 받는다. Orca·herdr와 달리 `opencode.json`을 쓰지 않는다.
- `runtimeMode`는 빼서 관리자의 것을 물려준다. 좁은 모드는 사람의 승인을 기다리며 멈춘다.

## 제출 확인

`delegate_task`가 `taskId`를 돌려주면 시작된 것이다. 오류나 응답 유실이면 같은 `clientRequestId`로 한 번 다시 부른다. 같은 일을 새 `clientRequestId`로 두 번 띄우지 않는다.

## 기다리기

- **관리자**: 이슈 담당은 `async`로 띄우고 기다리는 동작을 따로 하지 않는다. 이슈 담당이 끝나거나 질문을 열면 T3가 관리자를 깨운다. 도구 결과의 `next`를 따르고, `task_status`·잠자기·반복 조회로 기다리지 않는다. 기다리는 동안 다른 일(다음 이슈 고르기 등)을 한다.
- **이슈 담당**: 한 이슈만 맡으므로 작업자를 `mode: "wait"`로 띄워 결과를 바로 받는다(`timeoutMs`는 최대치로). 대기가 끝난 이유를 본다.
  - `hasPendingQuestion: true`: 작업자가 질문을 열었다. 아래 "답하기".
  - `pendingApproval`: 권한 승인이다. 부모는 대신 승인할 수 없으니 질문 도구로 관리자에게 알리고, 관리자가 사용자에게 알린다.
  - `waitTimedOut: true`: 작업자는 계속 돈다. `t3_thread_wait`(`childThreadId`)로 다시 기다린다.
  - 그 밖에는 완료다. 결과의 `summary`가 완료 보고다.

## 답하기

`t3_pending_request`에 작업자 스레드(`childThreadId`)를 주고 `list` → `read`로 질문을 본 뒤, `respond`로 `answers`(질문 문장 → 고른 답)를 보낸다. 답한 뒤 다시 기다린다.

- 이슈 담당이 명세·이슈·프로젝트 설정으로 답할 수 없는 질문은, 이슈 담당이 질문 도구로 관리자에게 다시 묻는다. 관리자는 같은 방법(`t3_pending_request`, 이슈 담당 스레드)으로 읽고 답하거나 사용자에게 묻는다.
- 권한 승인 요청은 `t3_pending_request`로 답할 수 없다. 사람이 그 스레드에서 직접 승인해야 한다.

## 보내기

남겨 둔 작업자에게 다음 지시(지적 수정, 재검토)는 `t3_thread_send`(`threadId`: 그 작업자의 `childThreadId`)로 보낸다. 끝난 작업자에게 보내면 같은 스레드에서 새 작업이 시작되고 새 `taskId`가 온다. 그 스레드의 맥락과 worktree를 그대로 쓴다.

관리자가 6단계에서 이슈 담당에게 일을 다시 맡길 때(rebase, "리뷰 반영해")도 이슈 담당 스레드에 `t3_thread_send`로 보낸다. 관리자는 이슈 worktree에 작업자를 직접 띄울 수 없다.

## 남겨 두기

아무것도 하지 않는다. 끝난 작업자 스레드는 그대로 남고 `t3_thread_send`로 다시 맡길 수 있다.

## 정리

그 작업의 작업자와 이슈 담당 스레드마다, 아직 돌고 있으면 `task_cancel`(`taskId`)로 멈추고, `t3_thread_organize`의 `archive`로 보관한다.

## worktree 지우기

정리(보관)를 먼저 한다. 그다음 `git -C <메인 저장소> worktree remove <worktree 경로>` 뒤 `git -C <메인 저장소> branch -D <작업 이름>-<slug>`.

- T3가 끝난 세션의 폴더를 한동안 잡고 있어서 폴더 삭제가 "busy"나 "Permission denied"로 실패할 수 있다. `git worktree remove`가 git 등록은 지웠으면(`git worktree list`에 없으면) 빈 폴더만 남는다. 스레드를 보관하고 몇 분 지나면 풀리므로, 다음에 깨어날 때 `rm -rf <worktree 경로>`와 `git worktree prune`을 한 번 더 한다. 계속 남으면 사용자에게 경로를 알린다.

## 작업자가 보고하는 방법

명세 양식의 `{실행 환경: 완료 보고}`와 `{실행 환경: 질문}`에 넣는 문장이다.

- 완료 보고(구현자): "완료 보고는 마지막 답으로 한다. 같은 내용을 `<작업 폴더 절대 경로>/<제목>-report.md`에도 쓴다. 하위 에이전트는 띄우지 않는다."
- 완료 보고(검토자): "보고서를 다 쓰면 마지막 답에 보고서 경로와 결론(통과 / 수정 필요)만 3문장 이내로 적는다. 하위 에이전트는 띄우지 않는다."
- 질문: "질문은 질문 도구(AskUserQuestion)로 하고 답을 기다린다."

## 이슈 담당에게 맡기는 글

관리자가 `<...>`를 채워 이슈 담당의 `task`로 준다. 이슈 담당은 맥락 없이 시작하므로 경로는 모두 절대 경로다.

```markdown
# <작업 이름> 이슈 담당

당신은 이슈 <이슈 표시>의 담당입니다. 이 worktree에서 구현자와 검토자를 띄워 교차 검토를 통과시키고, 결과를 돌려줍니다. 코드는 직접 쓰지 않습니다.

## 읽을 것

- 지휘 규칙: `<스킬 폴더>/SKILL.md`의 "고정 규칙"과 2단계 3부터 5단계까지. 당신이 할 일은 여기까지다. 6단계(PR·병합)는 하지 않는다.
- 실행 환경: `<스킬 폴더>/backends/t3.md`. 당신은 "이슈 담당" 쪽 동작을 한다.
- 프로젝트 설정: `<프로젝트 설정 절대 경로>`
- 작업 폴더: `<작업 폴더 절대 경로>` (명세 `task.md`, `state.md`, 보고서가 여기 있다)

## 정한 것

- 등급: <등급>
- 구현자: <표기>
- 검토 목록: <검토 목록 표기>. 구현자와 같은 계열은 건너뛴다.
- 한도: <측정 결과 한 줄>. 판정에 따른 처리는 `<스킬 폴더>/limits.md`.

## 처음에

1. `git branch -m <작업 이름>-<slug>`로 브랜치 이름을 바꾸고, `t3_worktree_status`의 경로와 브랜치를 `state.md`에 적는다.
2. `orchestrator_capabilities`를 한 번 부른다.
3. Codex 작업자를 띄웠으면 첫 응답 뒤 `$CODEX_HOME/sessions/`(없으면 `~/.codex/sessions/`)에서 `cwd`가 이 worktree인 가장 새 세션 기록의 `"service_tier"`가 정한 값인지 보고 `state.md`에 적는다([codex-fast.md](../codex-fast.md) "적용").

## 끝나면

마지막 답에 다음을 적는다: 결론(통과 / 사용자 결정 필요 / 실패), 브랜치, worktree 경로, 마지막 커밋 해시, 검토 보고서 경로, 테스트 결과, 다른 이슈로 넘긴 지적, 사람이 직접 확인할 항목.

사용자만 정할 수 있는 결정은 질문 도구로 묻는다. push, PR, `main` 병합은 하지 않는다.
```

## 지휘 현황 패널

T3는 Claude Code 화면을 쓰지 않아 지휘 현황 패널과 띠가 보이지 않는다. 현황은 `state.md`와 관리자의 보고로 본다. 사용자가 현황을 물으면 `.local/orchestration/*/state.md`를 훑어 단계별로 알린다. 작업자 스레드는 T3 화면에서 직접 열어 볼 수 있다.
