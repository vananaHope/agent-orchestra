# 명세 새 눈 점검

관리자는 대화와 이슈를 다 알아서, 명세에서 빠진 것을 스스로 알아채기 어렵다. 맡기기 전에 맥락이 없는 에이전트에게 명세만 보여 주고, 이대로 시작하면 무엇을 물어야 하는지 받는다. 작업자가 `ask`로 되묻거나 검토에서 "명세와 다르다"로 돌아오는 일을 줄이려는 것이다.

## 언제

- `standard`·`hard` 구현과 UI 구현의 명세(`task.md`)를 처음 쓴 뒤, 맡기기 전에 한 번 한다.
- `light`, rebase, 지적 수정([fixes.md](fixes.md)), 검토 명세에는 하지 않는다.
- 앞부분 작업은 그 등급을 따른다.

## 누구에게

1. OpenCode `plan` 에이전트(읽기 전용)에게 메인 저장소에서 묻는다: `opencode run --agent plan "<질문>"`. 1분 안팎이 걸린다.
2. OpenCode의 한도가 `ok`가 아니거나 쓸 수 없으면, Agent 도구로 새 서브에이전트를 띄워 같은 질문을 준다. 이 대화의 내용은 넣지 않는다.

## 질문

```text
<task.md 절대 경로>를 읽어라. 명세가 "먼저 읽을 것"으로 적은 파일과 저장소의 코드는 읽어도 된다. 이 대화나 관리자의 의도는 모른다고 보고, 이 명세만으로 구현을 시작한다고 하자.
시작하기 전에 관리자에게 꼭 물어야 할 것을 최대 7개 적어라. 해당하는 것은 셋이다: 뜻이 둘 이상으로 읽히는 지시, 정해지지 않았는데 구현에 필요한 정보(위치, 이름, 동작, 완료 판정), 서로 맞지 않는 지시(명세와 명세, 명세와 코드).
각 질문에는 명세의 해당 줄(또는 절 이름)과, 왜 그대로는 시작할 수 없는지를 한 줄로 붙여라. 코드 스타일 취향이나 명세가 이미 답한 것은 적지 말라. 물을 것이 없으면 "없음"이라고만 답하라.
```

## 답을 받은 뒤

질문마다 셋 중 하나로 처리한다.

- **반영**: 이슈, 프로젝트 설정, 코드에서 답을 찾을 수 있으면 그 답을 `task.md`에 적는다. 명세는 Write 도구로 고친다.
- **사용자에게 물음**: 제품 방향처럼 사용자만 정할 수 있으면 사용자에게 묻는다. 답을 기다리는 동안 그 이슈는 맡기지 않는다. 다른 이슈는 계속 맡긴다.
- **무시**: 명세가 이미 답했거나 이 이슈의 범위 밖이면 이유를 한 줄 적고 넘어간다.

같은 폴더의 `spec-check.md`에 질문과 처리(반영 / 사용자에게 물음 / 무시: 이유)를 한 줄씩 남긴다. 점검은 한 번만 한다. 반영한 뒤 다시 묻지 않는다.

**완료 기준**: `spec-check.md`가 있고, 모든 질문이 처리됐다(사용자에게 물은 것은 답을 받아 반영했다). "없음"이면 그렇게 한 줄 적는다.
