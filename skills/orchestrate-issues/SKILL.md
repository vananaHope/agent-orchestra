# 이슈 지휘

너는 **관리자**다. 코드는 직접 쓰지 않는다. 이슈를 작업 명세로 바꿔 작업자에게 맡기고, 다른 에이전트로 교차 검토하고, 판정하고, 병합한다.

## 시작하기 전에

- **프로젝트 설정**: 메인 저장소의 `docs/agents/orchestration.md`를 읽는다. 이 문서에서 "프로젝트 설정의 ○○"는 그 파일의 해당 절이다. 파일이 없으면 [setup.md](setup.md)대로 먼저 만든다.
- **자주 나온 지적**: `docs/agents/common-findings.md`가 이 프로젝트의 검토 지적 누적 목록이다. 명세와 검토에 이 파일의 절대 경로를 넣는다.
- **한도**: `check-limits` 스킬로 Codex와 Claude를 잰다. 다시 재는 때와 판정별 모드는 [limits.md](limits.md)에 있다.
- **스킬 폴더**: 이 스킬이 불릴 때 받은 기본 디렉터리(`Base directory for this skill`)다. 플러그인 버전이 바뀌면 경로도 바뀌므로, 명세에는 매번 지금 경로를 절대 경로로 쓴다.
- **Orca 명령**의 정확한 사용법은 이 문서에 없다. Orca 명령을 처음 쓰기 전에 `orchestration` 스킬을 불러 그 안내대로 `orca skills get orchestration`을 읽는다(버전에 맞는 안내가 그쪽에 있다).

## 배치

| 작업 | 구현 | 교차 검토 |
| --- | --- | --- |
| 코어 | Codex(`--agent codex`) | Claude(`--agent claude`) |
| UI(프로젝트 설정의 "UI 작업") | Claude | Codex |
| 간단한 구현([opencode.md](opencode.md)) | OpenCode Go | 관리자가 직접 확인 |
| UI 다듬기([ui-polish.md](ui-polish.md)) | 관리자 | Codex |

- 구현한 쪽과 다른 에이전트가 검토하는 것이 교차 검토다. 수정 작업자는 구현자와 같은 계열이다.
- 한 이슈에 코어와 UI가 섞여 있으면 UI 쪽을 Claude가 맡는다. 코어만 먼저 떼어 Codex에게 맡길 수 있으면 나눠도 된다.
- 한도가 `ok`가 아니면 이 배치는 [limits.md](limits.md)의 모드로 바뀐다.
- 넓게 훑어야 하는 짧은 질문은 OpenCode `plan` 에이전트에 먼저 묻는다([opencode.md](opencode.md)).

## 고정 규칙

- **새 작업 시작 조건**: 동시 구현 작업자 수에는 고정 상한이 없다. 검토자는 이 수에 넣지 않는다. 새 작업은 다음을 **모두** 만족할 때만 시작한다.
  - 새 작업을 맡을 에이전트의 한도가 `ok`다. Claude 검토가 뒤따르는 Codex 구현이면 Claude도 `ok`여야 한다.
  - 검토를 기다리는 작업(구현은 끝났는데 검토자가 아직 붙지 않은 것)이 1개 이하다.
  - 실창 잠금 대기가 길게 이어지고 있지 않다.
  - 새 작업이 진행 중인 작업과 같은 파일 영역을 건드리지 않는다.

  하나라도 깨지면 새 작업을 시작하지 않는다. 진행 중인 작업은 멈추지 않고, 끝나는 대로 수가 자연히 줄게 둔다. 같은 원인의 병합 충돌이 반복될 때도 새 작업을 멈춘다.
- **실창 검사**: 프로젝트 설정에 "실창 검사" 절이 있으면 모든 명세에 [desktop.md](desktop.md)의 세 가지를 넣는다.
- **추가 완료 조건**: 프로젝트 설정의 "추가 완료 조건" 절은 해당하는 이슈의 명세와 검토 양쪽에 그대로 넣는다. lint 같은 자동 검사가 못 잡는 조건(배치, 정보 밀도 등)일수록 양쪽에 넣어야 지켜진다.
- **병합 권한은 관리자.** 교차 검토가 통과하면 사용자 승인 없이 `main`에 병합하고 결과를 보고한다. 프로젝트 설정의 "병합 예외"만 사용자 승인을 받는다.
- **메시지 언어**는 프로젝트 `AGENTS.md`의 작성 규칙을 따른다. 정해져 있지 않으면 한국어다. 작업 명세, 커밋, PR, 이슈 댓글 모두.
- **작업 파일**(명세, 검토 보고서)은 메인 저장소의 `.local/orchestration/issue-<n>/`에 둔다. Git에서 제외되는 위치다.
- **확인 자료**: 사람이나 검토자가 실제 동작을 재현할 때 쓸 자료는 프로젝트 설정의 "확인 자료" 절에 있다.

## 단계

### 1. 프런티어 고르기

**이 단계는 묶음이 끝날 때만이 아니라 자리가 빌 때마다 바로 실행한다.** 병합, 작업자 정리, 이슈 닫힘이 있으면 묶음의 나머지를 기다리지 않고 곧바로 다시 고른다.

열린 이슈 중 `ready-for-agent` 라벨이 있고, 선행 이슈가 모두 닫혔고(`issue_dependencies_summary.blocked_by == 0`), 지금 진행 중이 아닌 것이 프런티어다. 시작 조건을 만족하는 동안 **임계 경로**에 있는 것부터 하나씩 고른다. 뒤에 이어지는 이슈 사슬이 가장 긴 이슈가 먼저이고, 같으면 번호가 작은 것이 먼저다.

**앞부분 착수**: 프런티어가 비었거나 다 맡겼는데도 시작 조건이 남으면, 막힌 이슈 중 선행 이슈의 파일을 건드리지 않는 부분(코어 로직, 스크립트, 테스트 등)을 "앞부분" 작업으로 나눠 시작한다. 이번에도 임계 경로 순서로 고른다.
- 명세에 "건드리지 말 파일·영역"과 "선행 이슈 병합 뒤로 미루는 범위"를 구체적으로 적는다.
- 해당 이슈에 앞부분과 마무리로 나눈다는 댓글을 남긴다.
- 앞부분은 같은 이슈 번호의 브랜치로 먼저 병합해도 되고, 마무리까지 한 브랜치에서 이어 가도 된다. 이슈는 마무리까지 끝났을 때 닫는다.
- 앞부분으로 떼어 낼 만한 부분이 작거나 선행 이슈와 겹치면 나누지 않는다.

**완료 기준**: 고른 이슈·앞부분 목록을 사용자에게 한 줄로 알렸다. 시작 조건이 남는데 맡기지 않았다면 그 이유도 한 줄로 알렸다(예: "앞부분으로 나눌 수 있는 이슈 없음", "검토 대기 2개").

### 2. 구현 맡기기

이슈마다:

1. [task-template.md](task-template.md)를 채워 `.local/orchestration/issue-<n>/task.md`로 저장한다. 명세 파일은 Write 도구로 쓴다(셸 heredoc을 거친 python 스크립트로 만들면 한국어가 깨진다). 이슈의 범위 밖 항목(다른 이슈가 맡은 기능)을 명세에 구체적으로 적는다.
2. Run이 없으면 만든다(이번 지휘 세션 전체에 Run 하나).
3. `worker-start --spec "<명세>" --worktree new-top-level --name issue-<n>-<slug> --base-branch main --agent <배치의 구현 에이전트>`로 시작한다.
4. **입력이 실제로 제출됐는지 확인한다.** `orca orchestration worker-read --dispatch <id> --source terminal --json`으로 작업자 화면을 읽는다. `draft`에 `[Pasted Content ...]`나 명세 일부가 남아 있으면 붙여넣기만 되고 제출되지 않은 것이다. 이때는 같은 명세를 다시 보내지 말고 `orca terminal send --terminal <handle> --enter`로 Enter만 보낸다.
   - 특히 기존 터미널을 재사용할 때(`--terminal`) 잘 생긴다.
   - `orca terminal read`의 결과에는 draft가 나오지 않으니 이 확인에 쓰지 않는다.

동시에 맡긴 이슈들이 같은 연결 지점을 각자 만들 것 같으면, 관리자가 그 **공용 계약** 파일을 `.local/orchestration/`에 직접 써서 "내용 그대로 복사"하라고 모두에게 보낸다. 같은 내용의 파일은 병합 때 충돌하지 않는다.

**완료 기준**: 맡긴 이슈마다 작업자 화면에서 "Working"이 보인다.

### 3. 기다리며 메시지 처리

`check --run <run> --wait --types "worker_done,escalation,question"`을 백그라운드로 돌려 **깨어나는 신호로만** 쓴다. 그 출력은 파일로 받든 grep을 거치든 한국어가 깨진다. 깨어나면 내용은 `check --run <run> --json | PYTHONIOENCODING=utf-8 python -I -c "..."`처럼 python으로 바로 넘겨 다시 읽는다. ack하기 전까지는 같은 묶음이 다시 나온다.

- **heartbeat**: ack하고 계속 기다린다. 사용자에게는 단계만 한 줄로 알린다.
- **question**: 이슈, 프로젝트 설정의 스펙·문서에 답이 있으면 답한다. 사용자만 정할 수 있는 결정이면 사용자에게 묻고, 받은 답을 전달한다.
  - 답은 반드시 `orca orchestration reply --run <run> --id <질문 msg_id> --body "..."`로 보낸다.
  - `send --to dispatch:...`로 보내면 작업자의 `ask`는 답을 받지 못하고 시간 초과된다.
- **worker_done**: 4단계로 간다.

메시지를 처리하기 전에는 ack하지 않는다.

### 4. 교차 검토

구현 작업자가 끝나면 그 작업자를 `worker-retain`으로 남겨 둔다(수정 지시에 재사용). 그다음 [review-template.md](review-template.md)를 채워 배치의 검토 에이전트를 **같은 worktree**(`--worktree "id:<worktree id>"`)에 새로 띄운다.

**완료 기준**: 검토 보고서 파일이 생겼고, 결론이 "통과" 또는 "수정 필요"다.

### 5. 판정

지적마다 셋 중 하나로 정한다.

- **지금 고침**: 차단·중요 지적 전부. 사소한 지적 중 고치는 비용이 작은 것.
- **다른 이슈로 넘김**: 다른 이슈의 범위에 속하는 것. 그 이슈에 댓글로 근거와 함께 기록한다.
- **사용자에게 물음**: 제품 방향을 정해야 하는 것.

"지금 고침"이 하나라도 있으면 [fixes.md](fixes.md)대로 수정을 맡기고 재검토하거나 직접 확인한다.

**테스트 범위**: 작업자와 검토자는 관련 테스트만 돌린다(명령은 프로젝트 설정의 "테스트" 절). 전체 테스트는 관리자가 Release 직전 `main`에서 한 번 돌린다.

**완료 기준**: 검토 결론이 "통과"이거나 [fixes.md](fixes.md)의 완료 기준을 채웠고, 넘긴 지적은 모두 해당 이슈에 댓글로 남았다. 검토에서 새 유형의 지적이 두 번째로 나왔으면 `docs/agents/common-findings.md`에 더했다.

### 6. PR과 병합

1. 브랜치를 push하고 [pr-template.md](pr-template.md)로 PR을 만든다(`Closes #<n>`).
2. `main`이 그사이 앞으로 갔으면, 해당 구현 작업자에게 `main` 위로 rebase하고 테스트를 다시 돌리라고 맡긴다. 충돌 해결도 작업자가 한다. "main 변경" 안내는 **진행 중인 Dispatch가 구현 작업일 때만** 보낸다. 검토 중인 이슈는 그 검토가 끝난 뒤 다음 구현 지시에 rebase를 넣는다(검토자에게 rebase 안내를 보내지 않는다).
3. `gh pr merge <PR> --merge --subject "<제목> (#<n>)"`로 병합하고, 원격 브랜치를 지우고, 메인 저장소의 `main`을 pull한다.
4. 작업자들을 `worker-release`로 정리한다. 재사용한 터미널은 `retained`(`user_takeover` 등)로 남을 수 있다. `worker-list --run <run> --terminal-state reclaimable`이 0이면 정리가 끝난 것이다.
5. **병합한 worktree는 바로 지운다**(디스크 용량 확보: worktree마다 의존성 설치와 빌드 결과가 있어 크다). 지우기 전에 셋을 확인한다.
   - 그 worktree의 `HEAD`가 `origin/main`에 들어 있다: `git merge-base --is-ancestor <HEAD> origin/main`
   - 커밋하지 않은 변경이 없다: `git -C <worktree> status --porcelain`이 비었다.
   - 그 worktree를 쓰는 작업자 터미널이 남아 있지 않다. 남아 있으면 먼저 닫는다.

   셋 다 맞으면 `orca worktree rm --worktree path:<worktree 경로>`로 지운다. 병합된 로컬 브랜치도 함께 지워진다. 하나라도 어긋나면 지우지 않고 사용자에게 이유를 알린다.
   - **앞부분만 병합하고 마무리를 같은 worktree에서 이어 갈 이슈**는 지우지 않는다. 마무리까지 병합한 뒤 지운다.
   - 관리자가 직접 쓰는 worktree(예: UI 다듬기)도 같은 규칙을 따른다. 병합 전에는 지우지 않는다.
   - 작업 파일(명세·검토 보고서)은 메인 저장소의 `.local/orchestration/`에 있으므로 worktree를 지워도 남는다.

6. 바로 1단계로 가서 빈 자리를 채운다. 새로 풀린 이슈와 앞부분 작업을 확인한다. 7단계 보고를 기다리지 않는다.

**완료 기준**: 이슈가 닫혔고, `main`이 원격과 일치하고, 정리할 작업자가 0명이고, 병합한 worktree가 지워졌고, 1단계를 다시 실행했다.

### 7. 보고하고 다음 묶음

사용자에게 이슈마다 결과(PR 링크, 테스트 수, 검토 횟수와 주요 지적, 넘긴 지적, 시스템 변경)와 **사람이 직접 확인할 항목**을 모아 보고한다. 확인 자료가 있으면 그 위치를 안내한다. 자리 채우기는 6단계에서 이미 했으므로, 보고에는 지금 진행 중인 작업 목록만 덧붙인다. 화면 묶음의 구현 이슈가 모두 병합됐으면 [ui-polish.md](ui-polish.md)를 시작한다.

**완료 기준**: 열린 `ready-for-agent` 이슈가 없거나, 사용자가 멈추라고 했다.
