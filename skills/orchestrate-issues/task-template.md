# 구현 작업 명세 양식

`<...>`를 채워 구현 작업자에게 보낸다. `{설정: ○○}`는 프로젝트 설정(`docs/agents/orchestration.md`)의 해당 절 내용을 그대로 옮긴다. 이슈별로 바뀌는 곳은 Change와 범위 밖 목록뿐이다.

```markdown
# 작업: GitHub 이슈 #<n> "<이슈 제목>" 구현

당신은 이 작업의 구현 담당입니다. 끝나면 관리자(Claude)가 별도 에이전트로 교차 검토합니다.

## 먼저 읽을 것 (필수)

- `gh issue view <n> --comments` : 완료 기준 체크리스트와, 앞선 이슈에서 넘어온 지적(댓글). 이것이 기준이다.
- {설정: 스펙과 먼저 읽을 문서}

## Target

현재 worktree(`main`에서 분기한 이 작업 전용 브랜치). <이 이슈가 주로 건드릴 영역>

## Change

이슈 #<n>의 완료 기준을 모두 만족시킨다. <기준을 짧게 요약하고, 이슈 댓글로 넘어온 지적이 있으면 함께 처리하라고 적는다.>
<해당하면: {설정: 추가 완료 조건}>

## Constraints

- {설정: 구현 제약}
- 범위 밖(다른 이슈가 맡음, 만들지 않는다): <이슈 번호와 기능 목록>. 그것들이 들어올 자리를 막는 구조로도 만들지 않는다.
- 커밋 메시지는 <프로젝트 작성 규칙의 언어>. 의미 단위로 여러 번 커밋해도 된다. push, PR 생성, `main` 병합은 하지 않는다.
- 이 worktree 밖의 파일은 건드리지 않는다. 시스템 수준 설치나 업그레이드가 필요하면 해도 되지만, 무엇을 했는지 완료 보고에 적는다. 검증 기록은 저장소에 커밋하지 말고 완료 보고에 담는다.
<실창 검사 절이 있으면: desktop.md의 세 가지(잠금 명령은 스킬 폴더 절대 경로로)와 {설정: 실창 검사}.>

## Ownership

이 worktree 안의 파일만 편집한다. <다른 작업자가 동시에 진행 중인 이슈가 있으면: "#<m>이 동시에 진행 중이며 <영역>을 건드린다. 공용 부분을 바꿀 때는 그 사실을 완료 보고에 적는다.">

## 테스트 실행

- 바꾼 모듈과 직접 관련된 테스트만 돌린다. {설정: 테스트}
- **전체 테스트는 돌리지 않는다.** 전체 테스트는 관리자가 Release 직전 `main`에서 한 번 돌린다.
- 동시 실행 반복, 결함 주입 반복, 전후 시간 비교 같은 추가 측정은 명세가 요구할 때만 한다.
- 부하 때문에 시간 초과가 나면 다시 돌리지 말고 보고에 적는다.

## 제출 전 자기 점검

`<메인 저장소>/docs/agents/common-findings.md`(자주 나온 검토 지적)를 읽는다. 이번 변경에 해당하는 유형마다 그 "점검"을 실제로 해 본다. 완료 보고에 유형별로 "해당 없음 / 확인함(방법) / 남김(이유)"을 한 줄씩 적는다.

## Observable acceptance

- `gh issue view <n>`의 완료 기준이 모두 충족된다.
- 환경은 {설정: 환경 준비}로 준비한다.
- 바꾼 모듈과 관련된 테스트가 통과한다. 전체 테스트는 관리자가 Release 직전에 돌린다.
- 자기 점검 결과가 완료 보고에 있다.
- `worker_done` 요약에 다음을 담는다: 커밋 해시, 테스트 결과(통과 수), 설치하거나 바꾼 시스템 구성 요소, 사람이 직접 확인해야 할 항목, 충족하지 못했거나 판단이 필요했던 항목.
- 막히거나 스펙이 모호하면 추측하지 말고 orchestration `ask`로 관리자에게 질문한다.
```
