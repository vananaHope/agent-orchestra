# 교차 검토 명세 양식

`<...>`를 채워 검토자에게 보낸다. `{설정: ○○}`는 프로젝트 설정의 해당 절 내용을, `{실행 환경: 완료 보고}`는 실행 환경 문서 "작업자가 보고하는 방법"의 검토자용 문장을 그대로 옮긴다. 보고서 경로는 `.local/orchestration/<작업 이름>/`의 절대 경로로 쓴다(검토자는 worktree에서 실행된다).

```markdown
# 작업: 이슈 <이슈 표시> 구현의 교차 검토 (검토 전용, 파일 수정 금지)

당신은 교차 검토자입니다. 다른 에이전트(<구현 에이전트>)가 이 worktree에서 이슈 <이슈 표시>를 구현했습니다. 구현 과정의 맥락 없이 결과물만 보고 독립적으로 판단하세요.

## 먼저 읽을 것

- 이슈 내용과 앞선 이슈에서 넘어온 지적: <GitHub면 `gh issue view <n> --comments`. 다른 저장소면 구현 명세의 "이슈 본문"을 그대로 옮긴다.>
- 완료 기준(판정 기준): <구현 명세의 "완료 기준"과 같은 위치나 같은 목록>
- {설정: 스펙과 먼저 읽을 문서}
- 변경 내용: `git log --oneline main..HEAD`, `git diff main...HEAD`

## 검토 항목

1. **완료 기준**: 항목마다 충족 / 미충족 / 자동 확인 불가(사람이 봐야 함)를 판정하고 근거(파일·테스트 이름)를 단다. <해당하면: {설정: 추가 완료 조건}도 같은 방식으로 판정한다.>
2. **테스트 실제 실행**: 변경과 관련된 테스트만 한 번 돌려 결과를 기록한다. {설정: 테스트} 전체 테스트는 돌리지 않는다(관리자가 Release 직전 `main`에서 돌린다).
3. **자주 나온 지적**: `<common-findings.md 절대 경로>`의 유형을 먼저 확인한다. 구현자의 완료 보고에 있는 자기 점검 결과가 맞는지도 확인한다.
4. **구현 제약**: {설정: 구현 제약}을 지키는가. ADR이나 프로젝트 문서와 어긋나는 곳이 있는가.
5. **테스트 품질**: 공개 동작을 검증하는가, 내부 구현에 묶였는가. 중요한 동작인데 테스트가 없는 것은.
6. **용어**: 도메인 이름이 프로젝트 용어집(있으면)과 맞는가. 용어집에 없는 개념이 생겼거나 피하라고 한 단어를 쓰는가.
7. **범위**: 다른 이슈의 기능을 미리 만들었는가(과잉). 그것들이 들어올 자리를 막는가.
8. **위생**: 큰 바이너리, 가상 환경·의존성 폴더, 검증 기록 파일이 커밋되지 않았는가. 커밋 메시지가 프로젝트 작성 규칙의 언어인가. 비밀 정보나 하드코딩된 절대 경로가 없는가.
9. **버그**: 위와 별개로 실제 동작을 깨뜨리는 결함. 실제 외부 도구나 자료로 재현해 볼 수 있으면 재현한다. {설정: 확인 자료}

## 제약

검토 전용. 파일을 수정하거나 커밋하지 않는다. 임시 스크립트는 worktree 밖에서 돌리고 흔적을 남기지 않는다. 추측성 지적은 하지 않고, 지적마다 재현 방법이나 근거(파일과 줄, 실행 결과)를 붙인다. 화면을 직접 띄워 보는 확인은 사람 몫이다.

## 결과

상세 결과를 `<보고서 절대 경로>`에 쓴다. {실행 환경: 완료 보고}

- 결론: 통과 / 수정 필요
- 검토한 커밋: 검토한 worktree에서 `git rev-parse HEAD`로 확인한 전체 해시
- 완료 기준 판정표 (항목 / 판정 / 근거)
- 테스트 실행 결과
- 지적 목록: 심각도(차단 / 중요 / 사소) · 내용 · 근거 · 제안
- 사람이 직접 확인해야 할 항목
```

## 재검토

지적 수정의 재검토는 **차단·중요 지적을 고쳤을 때만** 한다(SKILL.md 5단계). 사소한 지적만 고쳤으면 관리자가 직접 확인한다. 병합 직전 SHA가 달라진 경우는 SKILL.md 6단계의 기준을 따른다.

지적 수정의 재검토는 남겨 둔 같은 검토자에게 짧은 명세로 맡긴다. 병합 직전 SHA 변경의 재검토는 SKILL.md 4단계와 같은 방법으로 같은 worktree에 검토자를 띄운다.
- 대상: `git diff <이전 커밋>..HEAD`와 브랜치 전체
- rebase 뒤 재검토면 위 diff 대신 `git range-diff <옛 base>..<검토 통과 SHA> origin/main..<PR head>`의 확인 대상 부분을 본다. `<옛 base>`는 `git merge-base <검토 통과 SHA> origin/main`이며, `git rev-list --merges <옛 base>..<PR head>`에 병합 커밋이 있으면 range-diff에 보이지 않는 충돌 해결·변경도 본다. 병합 뒤 사후 확인의 범위와 확인 대상 판정은 SKILL.md 6단계를 따른다.
- 판정 대상: "지금 고침"으로 정한 지적 목록. 넘긴 지적은 판정하지 않는다.
- 병합 직전 SHA 변경으로 맡긴 재검토면 6단계에서 확인 대상으로 정한 차이를 판정한다.
- 앞선 재현 절차를 다시 돌려 확인하고, 새 결함이 있는지 본다.
- 테스트는 수정분과 관련된 것만 돌린다. 전체 테스트는 돌리지 않는다.

보고서는 `rereview-<k>.md`로 따로 쓴다. 결론(통과 / 수정 필요)과 **검토한 커밋**(검토한 worktree에서 `git rev-parse HEAD`로 확인한 전체 해시)을 함께 적는다.
